# Star Captain — Project Notes for Claude

This file captures project-specific context and hard-won lessons. Read it before
making non-trivial changes — especially anything that touches Unity UI scenes,
the MainMenu builder, or layout code.

## Project basics

- **Engine:** Unity 6 (`6000.4.8f1`). Treat any "Unity 6 changed X" hypothesis
  skeptically — most uGUI behavior (`LayoutGroup`, `Mask`, `ScrollRect`) is
  unchanged from earlier versions. Verify against Unity's release notes for that
  exact subsystem before rewriting around an alleged regression.
- **Unity project root:** `SpaceGame/` (the inner folder — contains `Assets/`,
  `Library/`, `ProjectSettings/`).
- **Target:** mobile (landscape, 1920×1080 reference resolution, blend match=0.5
  on `CanvasScaler`).
- **Render mode:** Screen-Space Overlay.
- **Text:** TextMeshPro everywhere — never `UnityEngine.UI.Text`.
- **Persistence:** SQLite via SQLitePCLRaw; saves managed by `DatabaseManager`
  under `GameManager`.

## How the MainMenu scene gets built

The `MainMenu.unity` scene is **generated by an editor script**:
`Assets/Scripts/Editor/MainMenuSceneSetup.cs`, menu item
**Star Captain → Setup Main Menu Scene**. That script also wires up
`MainMenuController` and `PortraitPickerPanel` serialized references via
`SerializedObject.FindProperty` and string paths.

The saved `.unity` file is therefore a snapshot of whatever the builder produced
the last time someone ran the menu item. If the builder code is later modified,
the scene will not reflect those changes until the menu item is re-run and the
scene is saved.

`MainMenu.unity` is ~9,600 lines of Unity YAML with tightly coupled internal
fileIDs. **Never hand-edit it** except to patch a single isolated property in
an emergency. The build script is the canonical source of truth — make
structural changes there, then regenerate.

### Rule: keep builder code and saved scene in sync

When you change `MainMenuSceneSetup` (hierarchy, names, anchors, components):

1. Open a **fresh empty scene** in Unity (File → New Scene → Empty).
2. Run **Star Captain → Setup Main Menu Scene**.
3. Save As → `Assets/Scenes/MainMenu.unity` (overwrite).
4. Commit the regenerated scene in the **same commit** as the builder change.

Running the builder into an existing populated scene can leave orphan objects
behind. Always start clean. Otherwise the next person to open the scene sees
stale UI and may chase phantom Unity-version bugs.

### Rule: hierarchy renames break `WireController` silently

`WireController` resolves references with `Find<T>(root, "Container/Header/...")`.
When `Set(so, "field", null)` is called with a missing target, **the serialized
field is silently overwritten with null** — no LogError, no compile failure,
just a NullReferenceException at runtime when something tries to use the panel.

If you rename or reparent any node inside a panel:

1. Update every matching `Find<T>` / `FindRT` path in `WireController`.
2. Grep the codebase for the old name to be sure.
3. Consider hardening `Set`/`Find` to `Debug.LogError` when a required reference
   resolves to null. The current helpers only warn on "property not found",
   which is the rarer failure mode.

### Wiring conventions in editor scripts

When an editor script assigns `[SerializeField]` references on a runtime
MonoBehaviour, always use the `SerializedObject` API — never reflection,
never `MonoBehaviour.field = ...` directly (it won't survive a domain reload).

The recipe is:

```csharp
var so = new SerializedObject(component);
so.FindProperty("fieldName").objectReferenceValue = target;
// ... more assignments ...
so.ApplyModifiedProperties();  // exactly once per object, at the end
```

Notes:

- `TMP_Text` is an abstract base class but serialises fine — wire
  `TextMeshProUGUI` instances directly into `TMP_Text` fields without casting.
- One `ApplyModifiedProperties()` per `SerializedObject` is enough; don't call
  it after every property or you'll generate noisy undo entries.
- `MainMenuSceneSetup.WireController` is the reference example for this
  pattern.

## Unity UI gotchas that bit us (none are Unity 6 specific)

### `ChildForceExpandHeight` overrides explicit `LayoutElement.flexibleHeight = 0`

`UnityEngine.UI.LayoutGroup.GetChildSizes` does
`flexible = Mathf.Max(flexible, 1)` when `ChildForceExpand` is true on the
parent. So setting a child's `LayoutElement.flexibleHeight = 0` to "pin" its
size **does nothing** if the parent has `ChildForceExpandHeight = true` —
every child still gets `flexible = 1` and shares the leftover space equally.

Symptom we hit: a 2px Divider with `flexibleHeight=0` grew to ~130px because
its parent `VerticalLayoutGroup` had `ChildForceExpandHeight=1`. The
ScrollView next to it shrank correspondingly and clipped its content.

**Rule:** if you need precise per-child heights, **don't use
`ChildForceExpandHeight` on the parent**. Use `ChildControlHeight` only, set
each child's `preferredHeight`, and leave `flexibleHeight` at -1. Or — better
for a fixed layout — skip the layout group entirely and use absolute anchors
(top-stretch with explicit `anchoredPosition` and `sizeDelta`). The current
`BuildPortraitPickerPanel` uses the absolute-anchor approach for this reason.

### `Mask + Image` requires alpha > 0

`UnityEngine.UI.Mask` reads the underlying `Graphic`'s alpha as the mask shape.
`Color.clear` (alpha=0) → empty mask → **nothing inside the masked area renders**.

Symptom we hit: the portrait picker's `Viewport` had `Image.color = Color.clear`,
so the entire scrolling grid was invisible.

**Rule:** for `Mask + Image`, use `Color.white` with `Mask.showMaskGraphic = false`
— the image's shape defines the mask, but the image itself doesn't draw. Better
alternative: use `RectMask2D` (no `Graphic` required, no stencil ops, cheaper
on mobile).

### Default RectTransform values are a smell

A child with `anchorMin=(0.5,0.5) anchorMax=(0.5,0.5) sizeDelta=(100,100) anchoredPosition=(0,0)`
in a saved scene means the builder code never explicitly sized it — those are
Unity's brand-new RectTransform defaults. Such children rely entirely on their
parent layout group to size them. The moment something nudges the parent's
behavior, the child snaps back to 100×100 in the middle of the parent.

**Rule:** every `MakeUIGO(...)` in scene-builder code should be followed by
explicit anchor/pivot/size assignments, even when a layout group is supposed to
override them. Belt and suspenders.

### `sizeDelta` is not a margin on stretched RectTransforms

When `anchorMin != anchorMax` on an axis, `sizeDelta` on that axis is
**distributed around the pivot**, not subtracted as a margin from the far edge.
With a centred pivot (0.5), `sizeDelta.x = -24` produces 12 units of inset on
each side, not 24 on the right.

For reliable margins on a stretched RectTransform, prefer one of:

- Pull the anchor itself in (e.g. `anchorMax.x = 0.95f`) — percentage-based,
  scales with the parent.
- Use `offsetMin` / `offsetMax` directly. `offsetMin = (left, bottom)` and
  `offsetMax = (-right, -top)` give you per-edge insets in canvas units (the
  approach `BuildPortraitPickerPanel` uses for the ScrollView).

Mixing `sizeDelta` with stretched anchors and expecting margin semantics is
the bug that produces "looks fine in editor, asymmetric on device" reports.

### Small canvas-unit values become sub-pixel on real devices

The canvas uses a 1920×1080 reference resolution with `matchWidthOrHeight = 0.5`.
On a 360×640 phone the effective scale factor is ~0.22 — so a 2-canvas-unit
divider renders as 0.44 device pixels and Unity rounds it to 0 or 1 inconsistently
across frames (shimmering line, sometimes invisible).

**Rule:** use percentage-based anchors for spacing whenever possible. Reserve
small absolute pixel offsets for borders, rules, and dividers — and when you do
use them, expect that anything < ~6 canvas units may disappear at the lowest
supported resolution. If a hairline divider matters visually, draw it with a
sprite or accept that it'll be 1 device pixel.

## Files to know

- `Assets/Scripts/Editor/MainMenuSceneSetup.cs` — generates the entire MainMenu
  Canvas + wires every `[SerializeField]` on `MainMenuController` and
  `PortraitPickerPanel`. This is where most UI-shape decisions live.
- `Assets/Scripts/UI/MainMenu/MainMenuController.cs` — runtime driver: panel
  switching, validation, ship-name randomizer, portrait selection callback.
- `Assets/Scripts/UI/MainMenu/PortraitPickerPanel.cs` — populates the portrait
  grid lazily on first open from `PortraitLibrary` (a ScriptableObject under
  `Assets/Resources/`). Built by **Star Captain → Build Portrait Library**.
- `Assets/Scripts/Data/PortraitLibrary.cs` — ScriptableObject holding the
  portrait textures + filenames.
- `Assets/Scenes/MainMenu.unity` — the saved snapshot; do not hand-edit unless
  you're patching a single property. Re-run the builder instead.

## When the user reports a UI bug

Before assuming a Unity-version or framework change, check this order:

1. Does the saved scene match the current builder code? (Read the YAML — look
   for nodes that exist in the scene but not in the builder, or vice versa.)
2. Are all `WireController` `Find*` paths still valid for the current builder
   hierarchy?
3. Is any `Mask` using `Color.clear`?
4. Is any `LayoutGroup` using `ChildForceExpand*` on children whose
   `LayoutElement.flexibleHeight/Width` is supposed to constrain them?
5. Only then consider Unity-version regressions.
